# Beat-em-up PoC: notes for Claude sessions

A first-person beat-em-up proof of concept in Godot 4.7.2 (GDScript with static typing, Forward+, Jolt, 60 Hz). The project owner, called **Game-boy** in the docs, plays each milestone build and signs it off. The design is [docs/SPEC.md](docs/SPEC.md), and the module contract is [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Start here
1. **Title your session "Beat-em-up: working session"** (`mcp__ccd_session_mgmt__set_session_title`) so the usage watcher can reach you. Then **read [docs/HANDOFF.md](docs/HANDOFF.md).** It is the live status: what's done, what's in flight, the exact next steps, and how to resume work that was cut off. Work moves between Claude accounts at every usage limit, so assume you're picking up someone else's work in progress.
2. Then read the current milestone plan in `docs/milestones/` and the parts of ARCHITECTURE.md your task touches.

## Run, test, look
- **Play:** `godot --path .`. The main scene is the Mission 1 level (Milestone 5); F6 cycles the crowd room, the training room and back.
- **Tests:** `tools/run_tests.sh` runs all GUT tests headless in about 5 minutes (293 s of test time at the end of M5, 1748 tests, on the shared 8 GB machine; M4 ended at 1588 tests and 267 s), using `--fixed-fps 60` so frame-timed tests are deterministic. `-gselect=<file>` runs one file. `-gjunit_xml_file=res://captures/<name>.xml` writes the per-file times. Read the full output for `SCRIPT ERROR`, `SHADER ERROR` and `ERROR`. `ART_PUNK_VARIANT_STRAIN=1` adds the strain runs of the Punk's three locked A/B variants (about 14 s).
- **Look at it:**
  - `tools/capture_combos.sh "<act title text>" 6` records combo-bot acts (`tests/bot/combo_bot.gd`) with Movie Maker into `captures/combos.avi`, plus `captures/bot.log` with the hits per act.
  - Tile stills with `ffmpeg -i captures/combos.avi -vf "fps=6,scale=480:-1,tile=5x4" -frames:v 1 sheet.png` and view them.
  - Judge visual work from captures, as Game-boy will, not only from tests.
- **Move data:** generated by `tools/gen_moves.gd`. Run `godot --headless --import --quit && godot --headless -s tools/gen_moves.gd && godot --headless --import --quit`. Edit values in the generator, never only in the `.tres` files.
- **Godot 4.7 API:** you can dump the class reference with `godot --headless --doctool <dir>`. Check APIs you're unsure of there; they changed across 4.x.

## Code rules
- **Style:** static types everywhere, tabs, `##` doc comments on public API, and comment density like the surrounding code.
- **No numbers in scripts:**
  - attack numbers go in move `.tres` files;
  - global tunables go in `game/autoload/tuning_data.gd`, as `@export_range` values in a group;
  - feel numbers are never script constants.
- **Layer boundaries:** simulation never reads a camera. Presentation (cameras, HUD, VFX, audio, rumble) only subscribes to `CombatEvents` and reads state; it never writes game state. `TimeController` is the one exception.
- **Spec changes need Game-boy's approval.** Record approved departures in README.md, "Where M1 departs from the spec" (add one section per milestone).

## Parallel work (important)
- The Workflow tool's `isolation: 'worktree'` **fails here**: the home folder `~` is itself a git repo with no commits, and the harness resolves to it.
- Instead, create worktrees yourself, for example `git worktree add .worktrees/<name> -b <branch> <base>` (`.worktrees/` is git- and Godot-ignored).
- Tell each agent its absolute worktree path and to `cd` there for every command. Each worktree needs its own `godot --headless --import --quit` first.
- Give each agent disjoint files to own. Merge the branches yourself afterwards.
- Pattern used throughout: build, then the lead's own look at the captures, then a lean adversarial review (mechanics, plus feel judged from captures), then one fix pass.
- **Which model and effort for which role, and the process rules that keep usage down** (from Milestone 5 on): docs/HANDOFF.md, "Model, effort and process rules from Milestone 5 on". The runners are `tools/workflows/build.js` (Sonnet builders) and `tools/workflows/review.js` (Opus visual lenses, Sonnet code lenses and skeptics). `tools/record_acts.sh` records a round's acts once, for every agent to share.

## Git
- Work happens on a milestone branch, `m<N>/<topic>`, with one PR per milestone into `main`. **Never merge a milestone PR until Game-boy signs it off.**
- Every commit message ends with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- PR descriptions end with `🤖 Generated with [Claude Code](https://claude.com/claude-code)`.
- Never commit `captures/`.

## Handoff protocol (every usage limit)
A low-cost **usage-watcher** session paces itself. It checks the plan usage every 30 minutes below 70%, every 15 minutes up to 85% and every 5 minutes above that (the account is a premium seat since 2026-10-25). At 90% of the 5-hour window or of the weekly limit, or sooner on a fast burn, it messages the working session to halt work and hand off. Work up to that 90% handoff; don't stop early. Size each launch to the headroom left below 90%. When a new phase or milestone doesn't fit, split off a first task that does, run it, and hand off at 90%. The rules and measured costs are in docs/HANDOFF.md, under "Usage rules for the working session".

On that message, or whenever you're near a limit:
1. Stop starting new work.
2. Commit work in progress on its branch (message prefix `wip:`), including inside `.worktrees/*`. Push every branch.
3. Update [docs/HANDOFF.md](docs/HANDOFF.md):
   - the state of each work package;
   - running workflows and agents, and what each was doing;
   - exact resume steps;
   - decisions since the last update;
   - anything Game-boy is waiting on.
4. Commit and push HANDOFF.md, then create the one-time resume task (HANDOFF.md, "Resume after a limit"), so the work restarts by itself after the reset. DM Game-boy on Slack only if something needs him.

Also update HANDOFF.md at every phase boundary, so a hard stop never loses more than one phase.

The watcher's instructions are in docs/HANDOFF.md, under "Usage watcher". If no watcher is running, start one as described there.
