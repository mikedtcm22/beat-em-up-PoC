# M3 judgement calls: S0-scaffold

Calls the S0 builder made where the plan left a gap or two readings. Each is a decision, an alternative not taken and why. Game-boy was not asked (no grey-block feel questions): the default that changes least was taken.

1. **`break_free(invuln_frames: int = -1)`, a default of "use `Tuning.grab_break_invuln_frames`".** A2.3 gives the signature `break_free(invuln_frames: int)`, and the S0 tunables list says `grab_break_invuln_frames` is "read by `break_free`". A call with an argument behaves as A2.3 says; a call with none reads the tunable. *Alternative:* a required argument, so the tunable is only read by the caller. *Why not:* it left the tunable with no reader in S0 and made every caller repeat the lookup. Also: it keeps the larger of a running invulnerability and the new one (`maxi`), so breaking free never shortens a get-up's, and it does nothing unless the body is GRABBED (a second call, or a stale one, can't grant free invulnerability).

2. **The armor hitstop rule skips only a victim that absorbed the hit and is not dead (`armor_absorbed and not killed`).** A2.6 says "a hit with `hit.armor_absorbed` puts only the attacker in hitstop". `receive_hit()` applies a killing hit in full (A2.2: "if `hit.armor_absorbed and not hit.killed`"), so a killed armored victim is a clean hit and freezes like any other. *Alternative:* the literal `hit.armor_absorbed`. *Why not:* the two files would disagree about a hit the armor rule is told never to absorb.

3. **`GameInput.menu_open` is written in one place in `TuningOverlay`, `_update()` (`menu_open = is_open()`), plus `_exit_tree()`.** The plan says one line on open and one on close. Every open and close goes through `_update()`, so one line covers both; the second is for an overlay freed while open (the room switch, a test), which would otherwise leave the fight held for good. `switch_room()` also clears it. *Alternative:* a line each in `set_panel_open()`, `set_cheats_open()` and `close_all()`. *Why not:* three places to keep in step.

4. **F6 from a scene that is neither room does nothing** (`GameInput.room_after()` returns "" for it). *Alternative:* go to `ROOM_SCENES[0]` from anywhere. *Why not:* the bots and the tests host a room inside their own scene; F6 there would throw the bot away. Run directly (`godot --path .` or a room's `.tscn`) it switches as specified. `other_room()` is the instance form, `room_after(path)` the pure one the test calls.

5. **Defaults the plan names a tunable for but gives no number: `windup_track_deg_per_s` 180, `windup_track_share` 0.5, `commit_pause_frames` 12, `boss_charge_chance` 0.4, `boss_pound_chance` 0.3, `boss_grab_chance` 0.3.** A tracking wind-up of 0.5 turns a 22-frame Punk wind-up (0.18 s of tracking at 180 degrees per second, about 33 degrees) toward a strafing player and then locks, so a sidestep after it misses; 12 frames (0.2 s) is a pause long enough to read as "I'm next"; the boss weights sum to 1 in the order the plan lists the attacks. *Alternatives:* the readability-first plan's tighter lock (a share of 0.35), a 20-frame commit. *Why not:* nothing in the plan favours them; P1-ai tunes them from the first-person sheets, and every one has a range wide enough for F1.

6. **`director_min_windup_gap_s` defaults to 0.35 s** (A2.10 replaces `director_min_attack_gap_s`, which was 0.35, and no `director_min_attack_gap_s` is declared). *Alternative:* the readability-first plan's 12 frames (0.2 s). *Why not:* A2.10 renames the Part C tunable, so its default carries over; the gate may lower it.

7. **`rear_warning_min_alpha` (0.65) is declared though Part B's brightness formula (`1 + step x (n - 1)`) does not use it**, because Part C's P1-hud section names it and A2.11 says S0 declares every named tunable. *Alternative:* leave it out. *Why not:* then P1-hud would have to append inside the group S0 had separated for it. P1-hud uses it or deletes it.

8. **`lunge` and `free_lunge` both widen to 0..8 m** (A2.7 names `lunge`). A boss charge or a jump kick uses `free_lunge`, and a range that capped at 4 would clamp it in F1. *Alternative:* only `lunge`. *Why not:* the travel `reach_m` includes is the `free_lunge` of an enemy move, since enemies have no magnetism.

9. **The `EnemyActor` skeleton starts in `AiState.POSTURE`, never wants a token, `windup_move()` returns the move unchanged and `enter_from()` only records its points.** "Stands idle" needed some state, and POSTURE is the one a standing enemy with no slot is in. *Alternative:* start in ENTER. *Why not:* nothing would ever leave it. P1-ai replaces all four.

10. **`EnemyCatalog.body_size()` of an unknown id, or a scene that does not exist, is a `CombatActor`'s default capsule**, read from an instance, not a literal. *Alternative:* `Vector2.ZERO` or an error. *Why not:* the cheat menu and the spawner call it for a size to look for room; a plausible capsule is safer than a zero one.

11. **The new named animations: `run_forward`, `hold_collar`, `held_collar` and `held_lift` loop; `taunt` and `brace` play once.** The plan marks `run_forward` and the last of the grab poses "(looping)" in one run-on list. The holds last as long as the grab does, and a non-looping clip would freeze on its last pose. *Alternative:* `hold_collar` plays once. *Why not:* a holder in GRABBING plays it for the whole mash window. The owners may change a flag in `LOOPING`.

12. **`PlaceholderAnims.build_move_with(poses, move, scale, ...)` and `windup_hold_time()` are public seams** (`build_move()` now calls the first). The plan asks for a test that `windup_hold_at` keys a clip, and no recipe uses it until P1-ai lands, so there was no way to key one from an id. *Alternative:* a test-only recipe id in `PlaceholderPoses`. *Why not:* it would ship a fake move id in game code.

13. **`ViewGeometry.forward(look_yaw)` is a fourth public function** (A2.1 names three). `PlayerCharacter.get_look_forward()` is that one expression; it lives next to the bearing maths so the formula for "the look's forward" exists once. The rest of the player's own `Vector3(-sin(look_yaw), 0.0, -cos(look_yaw))` lines are untouched (a minimal `player.gd` diff).

14. **`capture_bot.sh` takes two recording slots by default** (the plan's "two"), though the lead's note to builders says one Movie Maker window each: the slots are machine-wide, so each agent still records one at a time. `CAPTURE_SLOTS` and `CAPTURE_LOCK_DIR` override. A slot whose recorder died is taken over. Godot's `--resolution 1280x720` is overridden by the project's `window_width_override` and records at 1600 x 900, as `capture_combos.sh` always did; the sheets are scaled anyway.

15. **Enemy table rows may leave `unblockable` (false) and `guard_mult` (1.0) out, and `hitbox` may list several point spheres (`&"sphere:LeftFistPoint,RightFistPoint"`).** The plan's row format has one point; the Punk's shove and the Bruiser's smash have two. *Alternative:* one row per point. *Why not:* a move is one row.

16. **`stub_enemy` gives its token back to the director when its attack ends, is cut short or it is hit (`releases_token`, on by default), and with `attack_on_token` takes a granted token's turn** (asks `may_start_windup()`, then winds up). A2.12 asks only for `wants_token()` driven by a flag and a working `force_attack()`. The extras let P1-director, P1-hud and P1-instruments exercise a whole token loop against the real fixture with no AI. They are opt-in or harmless to a test that ignores them.

17. **`tests/test_enemy_move_checks.gd` is a small extra test file** (not in the plan's S0 list): it runs the shared helpers against the sparring dummy's jab, so the helpers are proven on a real move before the packages rely on them (its measured reach is 1.07 m against `reach_m` 1.05, inside the 0.15 m tolerance; a wild upper arm, knee and elbow are each refused). The checks are pure functions that return their problems (`clip_problems()`, `joint_problems()`, `reach_problem()`, `fp_telegraph_problems()`), with `check_*` wrappers that fail the test, so a test can see them fail. The first-person check looks only up to the held key: at the last startup frame the strike's fist is meant to be in front of the face.

18. **`tests/test_humanoid_rig.gd` gets the six new animation ids in its local lists** (the plan lets S0 touch it for table discovery only, but the test enumerates the ids and loops, and the new ones belong there).

19. **`tests/fixtures/stub_enemy.*` is S0's** (A2.12), so P1-room must not create its own `stub_enemy` (Part C lists one in its owned files).

20. **The pin order is a behaviour change to M2's player grabs** (the held body now always processes just after the player, where before it followed scene order). It is what 2.2 asks; all 537 M2 tests (the hold-view and launch-from-hold ones included) pass unchanged, and the "Jab" act's hit frames are the same as before.

21. **S0's own tests pin the contract, never the skeleton's behaviour, and `stub_enemy` replaces every behaviour hook of `EnemyActor`** (the control tick, `grant_token()`, `revoke_token()`, `set_slot()`, the move-finished and hit hooks, `wants_token()`, `force_attack()`), so it stands still the same way once P1-ai implements the base, and the director and base tests I wrote keep passing after P1-ai and P1-director merge. *Alternative:* assert what the skeleton does (a standing POSTURE enemy that never asks for a token, a director that always says go). *Why not:* those go red the moment a real implementation lands, and the fix would be an edit to an S0 file in the middle of phase 1. The tunables test checks that every planned tunable exists in its subgroup with its default, but lets a package append more inside its own subgroup. A deliberate retune of a default (the slice gate's locked values) is one edit to `TUNABLES` in `test_m3_contracts.gd`. P1-ai: `stub_enemy` has archetype `&"stub"` and no health tunable, so `EnemyActor._ready()` must cope with an archetype that names none (keep `max_health`).
