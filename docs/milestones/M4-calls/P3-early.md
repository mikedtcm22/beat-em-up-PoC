# M4 calls: P3-early

Package P3-early: the part of P3-int (M4-plan Part C section 8, as amended by A23) that needs neither the concept pick nor the real Punk, plus the slice gate's gaps 10, 12 and G1's gap 1 (M4-slice-gate.md) and F-motion's two requests to HumanoidRig (M4-calls/F-motion.md, part 5). It builds the showcase, the long take, the FP feel toggle of feel question 4, the L5 evidence act and the write-back guard so that they work unchanged when F-punk replaces the smoke Punk in place; P3-int proper re-records them then. Each call is the decision, an alternative not taken, and why. The machine was shared and loaded (1-minute load average 6 to 11), so every wall-clock figure is noisy; the pose, count and share figures are exact.

## 1. Calls

**C1. HumanoidRig's named libraries are dropped when the values they are built from change, compared by value, not by signal.**
- *Decision.* `HumanoidRig._on_motion_tuning_changed()` (one static connection to `Tuning.changed`, made the first time a library is asked for) reads `PlaceholderAnims.Life.from_tuning()` (every script variable of it, through `get_property_list()`, so a value F-motion adds to `Life` is watched without an edit here) when the property is `&""`, `move_speed` or begins `look_motion_`. If that signature differs from the one the cached libraries were built from, the cache is cleared and a static revision counter goes up. A rig compares the counter with its own at the top of `advance()` (one integer compare) and, when behind, takes the library the cache builds now (`_refresh_library()`): the cache key keeps its shape (`"<stance>@<scale x 10000>"`, tested), and the first rig to notice builds each key once for all the rigs of that size and stance.
- *Alternative.* Rebuild on every `Tuning.changed`, or drop the cache from each rig's own signal handler.
- *Why not.* Every test and every preset load ends with `Tuning.apply()` or `reset_to_default()`, which emit `changed(&"")`: rebuilding on that costs about 30 ms a key a call (about 4 keys, over 1,400 tests), and every live rig would fade into a copy of its own clip. Comparing values means a whole-set change that leaves the values as they were does nothing (tested: the cache keeps its library and the rig its library), and a change to an unrelated tunable does nothing. One side effect that is a fix: a test that set `look_motion_polish` directly and left a polish-off library in the cache used to leak it into the next test; the next whole-set change now drops it.

**C2. A rig that takes the new library goes on from the same share of the clip, faded in from the pose on screen.**
- *Decision.* If a clip of the named library is playing, `_refresh_library()` remembers `position / length`, swaps the library, and restarts the clip through the rig's own `_start()` (a fade of `locomotion_blend_s` from the pose on screen, as every start is) and seeks to `share x new length`. A move's clip (the per-rig "moves" library is never rebuilt) and a rig with nothing playing are left alone. A longer breath or a longer stride keeps the cycle's phase.
- *Alternative.* Restart at 0, or seek to the same second.
- *Why not.* Both pop: a walk of 0.185 s that becomes 0.37 s at half `move_speed` lands on a different foot. Tested: no watched point moves 2 cm across the swap or in the fade after it, for the idle (breath 4 s to 8 s) and the walk (`move_speed` halved).

**C3. The idle's own phase is for the crowd's bodies, from the name, by a Fibonacci hash.**
- *Decision.* A rig whose actor is in the group `ai_enemy` when it is built (EnemyActor joins it before it builds its body) starts and restarts its looped idle at `fposmod(hash(actor.name) x 0.618..., 1)` of the clip's length; every other rig (the player's, a training dummy's, a scratch rig's) starts at the first key as before. The share is read once at `build()`, so an actor that leaves the groups (a KO'd body, the showcase Punk) keeps it. Consecutive names (`Punk1` to `Punk6`) land evenly spread (0.0, 0.62, 0.24, 0.85, 0.47, 0.09 of a loop); tested pairwise at least 0.05 of a loop apart, and the same name gives the same phase in every run.
- *Alternative taken first, then dropped.* Every rig but the player's. The full suite then failed two tests that stood on a dummy's idle at phase 0: `test_ragdoll`'s "body launched from behind lands face down" (haymaker from behind: joints 11.3 degrees past a limit against the bar of 10; F-motion's C10 had said it sits on a knife edge, M3 9.97) and `test_combat_integration`'s spinning heel (the player's aim moved 0.0013 rad against a tolerance of 0.001, because his magnetism turns toward a dummy's chest, which breathes about 2 mm off the line at another phase). Other alternatives: a random generator (the brief rules it out), or a static build counter (order dependent: the phase of the n-th rig would depend on which tests ran before).
- *Why this.* The brief's purpose is "a wave spawned in one frame does not breathe and bounce in step": the crowd. A dummy stands alone and is a tuning target; the player's lens rides his head. No existing test changed, so no assertion was weakened and no twin is owed. The full suite is green with it (part 3).

**C4. The log's key is the overlay's own, and "hold it back" draws nothing without touching `visible`.**
- *Decision.* `CombatLogOverlay.TOGGLE_KEY` (L) is handled in the overlay's `_unhandled_input` (a press, not a release or a repeat) and flips `visible`, the state `GameHud.set_combat_log_visible()` and the bots use. `HelpOverlay.KEY_ROWS` lists it under the debug keys, read from the same constant. `combat_log_hide_while_holding` (Look > FP feel, false) makes `_process()` hold the overlay back while `player.holding_enemy()` is held by the player (`is_holding()`: a grab, and a knee that has not let go): `_draw()` draws nothing, the overlay keeps recording, `visible` is untouched, so the key and the hold are two things (tested: L off, then a hold, then the hold ends: still off).
- *Alternative.* An `InputMap` action `combat_log` in `GameInput.BINDINGS` (the way every other debug key is listed), and `GameHud` handling it.
- *Why not.* `game_input.gd` and `hud.gd` are not P3-early's: it goes in "requests". The row reads the constant, so moving the binding later changes one place.

**C4b. The showcase is a real Street Punk taken out of the game's systems, with Freeze AI saved and put back.**
- *Decision.* `CheatMenu.set_showcase(true)` instantiates the catalog's Punk scene (so it wears whatever the Punk wears, today the smoke art and F-punk's later), places it `showcase_distance_m` (1.0, an `@export_range` on the menu like its other spawn numbers) ahead of the player's feet along his look (the nearest clear spot when a wall or body is there), facing him, and calls `ShowcaseRunner.unplug()`: out of `enemy`, `ai_enemy` and `boss` (the director, the spawner's counts, the probes and "Remove all enemies" find enemies by those; it stays in `actor`, so the camera and the spawn clearance still know it is a body), off its physics tick, off the navigation avoidance, hurtboxes off. A `ShowcaseRunner` child plays `ShowcaseScript` on its rig by hand. While it shows Freeze AI is on; switching off frees the Punk and puts Freeze AI back to what it was, unless the player changed it meanwhile; a menu that leaves the tree (F6) does the same. Tested in both rooms: enemy, AI enemy, boss and actor counts, the director's token holders and queue, the spawner's alive count, `ai_frozen`, `waves_enabled`, god mode and the room's child count are the same after as before.
- *Alternative.* A bare `HumanoidRig` in a Node3D (nothing to unplug), spawned through the spawner, or one that takes real hits and reacts (ragdoll and all).
- *Why not.* A bare rig would be built by showcase code and drift from the Punk's own configuration (colors, art, variant switch) when F-punk changes it; the spawner would put it in the wave accounting; a live body that reacts to hits would interrupt the loop and needs the ragdoll's driver (CombatActor's), the thing the showcase does not run. The price: it cannot be hit (the take is the show; the DM text keeps "or fight live" for the crowd). Waves are left to the player: the DM's own order is "Waves off, then the showcase".

**C5. The take is a data table, its pacing in the file, its distances from the clips.**
- *Decision.* `game/debug/showcase_script.gd` holds `STEPS` (22 steps, 40.00 s): idle 5, a turntable (a full turn about its own vertical in 10 s, three extra marks), back off 1.2 m and walk in again at `posture_circle_speed_mps`, guard, taunt, jab (`punk_jab` with the AI's wind-up copy) and cross (the chain link as it is), takes a jab (`flinch_head_front`, the contact flash on the `EyePoint` with the hit's own tunables, bruised), stagger (slides 0.5 m back), knockdown (slides 1.0 m back), lying 2.5 s (bloodied), get-up, walk in again from 2.5 m, turn away, face-down fall (`knockdown_forward`, slides 1.0 m away), lying face down 2.5 s, face-down get-up, turn back, KO (`ko_back`, 3.0 s held). Seconds are the take's own pacing, authoring data like the pose files' numbers and the act files' tick counts, not feel; a clip step lasts its clip, a move step its move (`total_frames() / 60`), a walk the distance over the Tuning pace, and the table says nothing of the art. `test_showcase` holds the beats of the brief in order, the sum to 40 s (tolerance 1.5), and every clip, move and rig point to exist.
- *Alternative.* The beats as an `AnimationPlayer` track or a `.tres`; the lying bodies where they fall at 1 m.
- *Why not.* A `.tres` is a generator and a loader for 22 rows; and a Punk lying where it stands at 1 m puts its feet on the player's: measured at the clips' ends, a body is a metre long each way of its hips (`knockdown_back`: head 1.04 m behind, feet 1.0 m before; `knockdown_forward` the mirror), so the knockdowns slide the body (`slide_m`, a quadratic ease-out) until it lies 1 m or more from the lens: the face-up fall at 2.5 m, the face-down fall away from the lens (the Punk turns its back first) at 2.0 m, the KO at 2.0 m. That is the brief's "at 1-2 m" for gate gap 12, kept in the long take (not C5, whose launch and get-up are the real ones).

**C6. The long take is scripted through the runner, and its stills are taken after the pose is drawn.**
- *Decision.* `Look: Punk at 1 m, the long take` (slug `c14`) spawns a real Punk, takes it off the tick the way the turntable does (it stays in the enemy groups, so the next act's reset clears it), gives it a `ShowcaseRunner` with `auto_advance` off and steps it once per tick, `advance(dt); await bot._ticks(1)`, so the state a mark describes is the pose just drawn (LookRect's frame rule). A still is marked `TAKE_MARK_TICKS` (3) ticks into each step and at the middle of a step of a second or more; the contact flash lasts two frames, so a hit step has an extra `<name>_flash` still at its first tick; the turntable's quarters come from the runner's own marks. The view turns to a step's `view_pitch_deg` at 45 degrees a second (the lying bodies are below the lens) and is back at the default at the end. C15 `Look: F4 Showcase Punk` plays the cheat in the running game (below).
- *Alternative.* Real hits for the take's reactions (`receive_hit`, the ragdoll's partial and full), the Punk's own `force_attack` for the strikes.
- *Why not.* The showcase has to play the same script without a hit to land or a player to hit it, and two scripts would show two Punks; the reactions here are the pose clips F-motion polished (flinch, stagger, knockdown, downed, get-up, KO), without the ragdoll's physics. C5 and C11 stay the evidence of the real ones (and test_art_punk's write-back test, C9, runs the real ones on the real GLB).

**C7. C15 puts a crowd in the street, so "the game is as it was" means something.**
- *Decision.* The F4 act spawns two Punks from the alleys, opens the overlay as F4 does (`set_cheats_open(true)`), calls the toggle's own `set_showcase(true)`, closes it, has the player circle the frozen Punk once at the Punk's own circling pace looking at it, opens it and switches off. It logs `LOOK-SHOWCASE before / on / off` with Freeze AI (and what it was), and the enemy and AI enemy counts: after equals before. Tested headless.
- *Alternative.* A synthetic F4 key press and a click on the toggle.
- *Why not.* The key opens the overlay's embedded window in a real game; the toggle's `toggled` signal is the call made here, and a click needs a window in focus.

**C8. The L5 sampler is its own class, and it samples on the probe's cadence, both ways in the same fight.**
- *Decision.* `tests/bot/look_l5.gd` (`L5`): one instance per fight, `tick()` once a physics tick. R8 every `probe.lens_every` ticks on the probe's `lens_cols` grid: the proxies' figure is `FPView.hits()` (the probe's own measure); the drawn figure is the same grid with the view proxies hidden by an art rig's art taken out, in each cell the nearer of what is left and of `SkinnedView.hits()` (the triangles, every rig in the pose `SkinnedView.drawn_pose()` gives: a ragdolling rig in the ragdoll's visual pose). R4 every `probe.occlusion_every` ticks for each enemy in WINDUP whose chest is in the lens: another enemy's meshes as `FPView` counts them (the proxies, the probe's rule), and as drawn (a native `TriangleMesh` ray at the art's pose through `SkinnedView._soup()` and `_ray()`, its primitives as before when it has no art); the share of a wind-up's samples decides, as in the probe. It prints `LOOK-L5 <fight> R8 ...` and `LOOK-L5 <fight> R4 ...`. The act plays the two fights by calling the acts' own functions (`SliceActs._fight_six`, `CrowdActs._fight`), each from the look the act began with, the probe off.
- *Alternative.* Teach `readability_probe.gd` a drawn mode.
- *Why not.* The probe is another package's, its R4 and R8 are the hard rows of M3, and an act-level flag would make its numbers depend on which mode ran. This leaves them as they were and measures beside them. The two private `SkinnedView` calls (a single ray against the cached soup) are the instruments' own: a rename there fails the L5 tests, not the act silently.
- *Honest limits.* A wind-up is "an enemy in state WINDUP", polled each tick, not the probe's event; `r4` counts match the probe's on these fights (0 of 14 and 0 of 17), but the sampler's own proxies figure is the comparison, not the probe's JSON. Tested on small scenes with known answers (`test_look_l5`): the Punk ahead (the art and the proxies cover the view alike to 0.3 points, 2.1% of cells differ), art off (identical), the Kicker's primitives (identical), a launched Punk (cells that differ 0.8% mean, 2.3% worst, through 40 ticks of ragdoll), a wind-up behind a Punk, behind a Kicker, beside the blocker, in the open and behind the player.

**C9. Gate gap 10: a probe modifier on a real StreetPunk, with the figures outside the node.**
- *Decision.* `test_art_punk.gd` gets `test_a_modifier_after_the_ragdoll_sees_the_skeleton_equal_the_followers_through_a_real_punks_fight`: a real StreetPunk (`punk.glb`, the scene's art) on a stage with a floor, the AI frozen, god mode: its own jab, a stagger (the partial ragdoll), a launch out of the stagger (the full one), the get-up and a KO that frees it. A `SkeletonModifier3D` added to the skeleton after the Ragdoll exists (asserted: its child index is after the Ragdoll's) composes every bone's global pose from `get_bone_pose` and compares it, in rig space, with the bone's follower node (`rig.get_attachment(bone)`), on every update; a second one, added first, covers the jab. The control: a probe placed before the Ragdoll sees the raw simulator output, 0.01 m or more from the followers in a stagger, so the test has teeth. The rotation gap is measured exactly (`2 atan2(|v|, |w|)` of the delta): `Quaternion.angle_to()` reads 0.00098 rad for identical rotations, which sits on the bar.
- *Alternative.* Reuse `test_skinned_art`'s `PoseProbe` by preloading that test.
- *Why not.* It compares against `Ragdoll._visual`, not the followers, and a test file should not depend on another's inner class. The figures live in a `RefCounted` because a KO'd Punk frees the probe with its skeleton.

## 5. Requests and risks

- *GameInput / GameHud* (not mine): list the combat log's key as an input-map action (`&"combat_log": [KEY_L]`) so the help row comes from `GameInput.BINDINGS` like the others and a gamepad button can be given; `GameHud.is_combat_log_visible()` reads `visible` only (it does not know the overlay is held back: `CombatLogOverlay.is_showing()` does).
- *P3-int proper:* wire `fp_knockdown_hide_torso` (left alone, as asked); re-record C14, C15 and L5 on the picked Punk (the take's `slide_m` values come from the clips' ends, which F-punk does not change); the take's 3-tick stills may want a different delay once the real Punk's motion is seen.
- *HumanoidRig, F-motion's third request* (warm the Bruiser's and the boss's libraries in `RoomKit.warm_up_art`) is not in this brief and is not done.
- *Risk: the libraries rebuild on the main thread.* A slider drag on a Motion tunable rebuilds each key (about 30 ms) on the next tick that a rig advances, once per change; harmless in a debug panel, and a drag at 60 changes a second shows as a stutter while it lasts.
- *Risk: the knife-edge tests* (F-motion C10) still sit on dummies at phase 0; a future change that gives dummies a phase will flip two of them, and the right move then is not to give dummies a phase.
- *Risk: the showcase Punk is unhittable* by design; if Game-boy wants to hit it, the real Punk in the crowd is the thing to hit.
