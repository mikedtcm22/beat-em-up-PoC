**C2. final-v5-01: the Blender-free guard compares the first level of four step reports with the Punk's report.**
- *Decision.* `test_the_probe_report_has_the_step_report_keys_the_punks_report_has` (in `test_art_contract.gd`, after `test_each_character_report_names_the_glbs_it_exported`, so outside the Punk rows wave 2 edits): the key sets of `steps.inspect`, `fit`, `rig` and `palette` of `probe_report.json` and of the Punk's `report/report.json` are equal, and each failure names the keys and the command that fixes it. `parts_replace`, `parts_split` and `export` are left out on purpose: their keys follow the character's config (the Punk's `generated`, the probe's `caps` and `z_cut_m`, the Punk's `smooth_normals`). Only the first level is compared: the nested keys follow the data (`swatches_used` has a key per slot used, `fit.snap` a key per bone). Checked beforehand: after the regenerate these four are equal between the probe and the Punk, the heat-map Punk and the hero's reports.
- *Alternative.* Compare against every committed character report (Punk, heat-map Punk, hero). *Why not:* it holds today, but a hero or heat-map report that is regenerated later than a shared-step change would then fail the suite for something their own `--check` already says, and a package that changes a shared step would have to regenerate files it does not own. The Punk's report is the reference the plan's guard named, and the one a shared-step change regenerates first.
- *What it costs the next package.* A shared step that gains an unconditional report key (wave 2's palette step, say) turns this test red until `python3 -I tools/pipeline/make_probe_body.py` is rerun (the probe GLBs come out unchanged; only the report and its hash move) and the Punk's report is regenerated. That is the guard doing its job.
